## How to build the pages

- Every user-visible feature of the requirement maps to at least one page or section. Pages the requirement
  names come first, in its order; add only what a site of this kind clearly needs (and record it as an assumption).
- Use the built-in sections listed in `{{ sections_path }}` wherever they fit, with their typed `content`: these
  render without any model call. Use a custom component (in `components`, with a `propsSchema`) only for what no
  built-in section can show{% if mode == "dynamic" %}, typically a record view specific to this app{% endif %}.
- Theme: use the brand colours and fonts the requirement names. Without them pick the `theme.style` preset that
  suits the kind of site (`minimal`, `editorial`, `playful`, `corporate`, `dashboard`) and leave the colours to
  the preset, unless the requirement describes a mood they should follow.
- Images: one `assets` entry per image with a real `alt` text and `"source": "placeholder"`.

## Copy

- Use the words of the requirement. Headlines short (two lines at most), hero text 20 words at most.
- Never invent testimonials, client names or logos, figures, prices or awards. When the requirement gives none
  but a section needs them, write clearly generic sample content and record each one in `assumptions` as
  "sample content, replace before publishing".

## Notes

Write `{{ notes_path }}` as JSON:
`{"assumptions": [{"spec", "path", "message"}], "unresolved": [{"spec", "path", "message"}]}`, where `spec` is
`"frontend"` or `"backend"` and `path` a JSON pointer into that spec.
- Record every assumption (added pages, sample content, chosen theme, field types).
- Questions only the user can answer (who may edit or delete, prices and money rules, legal texts) go to
  `unresolved`. Do not guess them into the spec.
