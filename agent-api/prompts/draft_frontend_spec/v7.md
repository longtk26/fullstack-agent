## Drafting order for dynamic apps

1. **Journeys first**: write 2–5 `journeys` in the FrontendSpec representing the product's core loop first
   (for example, "learn vocabulary like Anki": browse decks, add cards, study due cards with ratings that reschedule
   them, see progress). Each journey has an `id`, `title`, optional `goal`, and a sequence of `steps` (`visit`, `open`,
   `submit`, `action`, `expect`). Step expectations test visible changes; use `live: true` only for expectations that
   require real backend scheduling or calculations (e.g. `dueDate` moved forward).
2. **BackendSpec second**: entities, standard CRUD operations, plus domain operations (`type: "custom"`) for steps
   CRUD cannot fulfill (e.g. scheduling algorithms, statistics, batch operations).
3. **FrontendSpec screens third**: design the user-facing journey screens using interactive sections (`DetailView`,
   `CardGrid`, `DataTable`, `ActionBar`, forms). The generated Manage area automatically covers uncovered operations and
   administrative CRUD for entities, so do not design generic admin screens yourself.
{% endif %}

## How to build the pages

- Every user-visible feature of the requirement maps to at least one page or section. Pages the requirement
  names come first, in its order; add only what a site of this kind clearly needs (and record it as an assumption).
- Use the built-in sections listed in `{{ sections_path }}` wherever they fit, with their typed `content`: these
  render without any model call. Use a custom component (in `components`, with a `propsSchema`) only for what no
  built-in section can show{% if mode == "dynamic" %}, typically a record view specific to this app{% endif %}.
- Navigation links (`layout.header.navigation`), footer links (`layout.footer.links`) and section CTAs (`page`) may
  only target pages without route parameters; detail pages are reached from a data section's record link.
{% if design_path %}- Design: `{{ design_path }}` lists three design briefs ranked for this requirement. Pick the one that fits
  best (the first unless another is clearly closer). Build the home page from its sections, in its order, with the
  requirement's content; leave out a section the requirement gives nothing for rather than inventing it. Do not
  choose colours, fonts or the hero layout yourself: the theme, the home page order and the hero `variant` are
  filled from the brief after you finish. Only if the requirement names brand colours or fonts, record them in the
  notes (below) and they win over the brief.
- Section variants are optional: `background` (`muted`, `primary`) can set off a section, `cardStyle` changes the
  cards of a list section. Use them sparingly; the defaults look right.
{% else %}- Theme: use the brand colours and fonts the requirement names. Without them pick the `theme.style` preset that
  suits the kind of site (`minimal`, `editorial`, `playful`, `corporate`, `dashboard`) and leave the colours to
  the preset, unless the requirement describes a mood they should follow.
{% endif %}{% if photos_enabled %}- Images and Photos: an image of a real-world subject (food, places, people at work, products, nature, culture, events) is `source: "photo"` with `kind: "image"` and a `prompt` that names the subject, the setting, the light and the framing, e.g. 'a steaming bowl of pho on a street stall table, morning light, close-up, shallow depth of field'. For collections and seed records with an image field, set the field to `asset:<entity>-<n>` and declare that asset with `source: "photo"`, a prompt describing that record (e.g. the dish's name and look), the collection's aspect ratio, and an alt text. Illustrations, logos, patterns and icons stay as they are (`"source": "generate"`, `kind` illustration/pattern/logo). Never write image URLs. At most {{ max_photos }} photos (records and pages share this cap); give them to the images that matter most (hero, key records). Other images stay generated drawings (at most 12).
{% else %}- Images: one `assets` entry per image (the hero, galleries, work samples, section backgrounds, the logo), each
  with a real `alt` text, and never a placeholder: every image is drawn. Give it `"source": "generate"`, a `kind`
  (`illustration`, `image`, `pattern` or `logo`) and a `prompt` that says what to draw for this site: a concrete
  scene or an abstract composition, without words in it. Drawings are flat vector art in the site's theme colours;
  when the requirement asks for photography, describe an editorial illustration of the same subject and record that
  as an assumption (the user can upload photos later). At most 12 drawn images per site.
{% endif %}

## Copy
