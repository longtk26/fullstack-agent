# Story 17.3 — Custom components: parallel engine calls & component cache

**Epic:** [17 — Fast generation](epic17_fast_generation.md) · **Requirements:** FR-30 · **Depends on:** 17.2

## User story

As a user, I want components the catalogue cannot express generated quickly, and a component that was already
generated and tested reused instead of written and tested again.

## Acceptance criteria

- [x] A custom component (a `components[]` entry used by a section) needs a props schema in the spec; the engine
      gets one call per component with its description, `uses`, props schema and the conventions, and writes one
      file with a default export. Calls run **in parallel** (bounded by a new setting `ENGINE_CONCURRENCY`, default 3), each in
      its own scratch copy of the frontend repo; only the component's file is taken back.
- [x] Each new component passes **isolated checks** before it is used: typecheck, lint, conventions and a render
      test with sample props generated from its schema. Failing ones go through the normal repair loop; one that
      still fails falls back to the closest catalogue section with a warning (never fails the generation).
- [x] **Cache key** = sha256 of the canonical JSON of {props schema, `uses`, normalized description, base lock
      sha (`overlay.json` `lockSha256`), overlay version, prompt version}. The component's name is not part of the
      key: cached files are stored as `src/components/custom/<key>.tsx` and the generated registry maps the
      spec's name to them. Engine and model are recorded, not keyed.
- [x] Only components that passed their isolated checks are stored (`component_cache` table + files under
      `ARTIFACT_ROOT/cache/components/<key>/`, with source generation, engine, hits, last used). A hit copies the
      files, skips the engine call and the isolated checks, and emits `component.cache_hit`; the site-level
      checks (build, routes, smoke) still run.
- [x] A cached component that breaks the site build is evicted and regenerated once. Changing the base, overlay
      or prompt version makes old entries miss on their own; an admin endpoint purges the cache.
- [x] Usage (8.x) shows cache hits and the engine time they saved; a report lists the most reused custom
      components as candidates for the catalogue.
- [x] `shop-dynamic`: 3 engine calls on the first run, 0 on the second.

**Status:** done (2026-10-29).

- **How it fits the renderer:** the planner lists a rendered site's custom components (those with a `propsSchema`;
  without one the site still goes to the engine) in `plan["customComponents"]`, each with a library fallback chosen
  from its section's binding (get → `DetailView`, list/collection → `CardGrid` / `DataTable` / `List`, else
  `RichText`). The scaffold registers the fallbacks, so a scaffolded site always builds; `generate_frontend`
  (`orchestrator/custom_components.py`) resolves each component and rewrites the registry, recording its new hash
  as generator-owned so the 17.5 auto-fix keeps it.
- **Isolated checks:** each component gets a scratch copy of the frontend and its own Node sandbox (a new `part`
  label, so it never touches the job's frontend sandbox): the nextjs-skills per-file rules (the same function as
  the site's `conventions` check), `tsc` on a tsconfig limited to the component and its test, ESLint, and a Vitest
  render test with sample props (schema samples + the props `SectionRenderer` would pass; dynamic: on the mock
  API, `$route.*` set to a fixture id; any `console.error` fails it). `ENGINE_CONCURRENCY` bounds engine calls and
  these sandboxes. Repairs use the job's repair limit; an engine failure or a component still failing falls back
  (`component.fallback`, never a failed lane). Without a sandbox (tests with the static validator) components are
  used but never cached.
- **Eviction:** when the site's typecheck or build fails, the cache hits it implicates (or all of this job's hits)
  are evicted once and regenerated by `repair_frontend` instead of an engine repair; it needs a repair attempt
  left (`maxRepairAttempts` ≥ 1).
- **Usage:** `totals.cacheHits` / `savedEngineMs` come from the user's own generations in the range;
  `catalogueCandidates` (most reused components) is in the admin view (`scope=all`) only. Purge:
  `DELETE /api/v1/cache/components` (admin).
- **Verified:** 442 tests without the Docker sandbox tests (11 in `test_component_cache.py`: key, samples, fallback, parallel bound, isolated repair,
  fallback on engine failure, no caching without a sandbox, eviction + regeneration, admin purge, first run 3
  calls / second run 0); Docker sandbox test `test_custom_components_pass_isolated_checks_then_come_from_the_cache`
  (real `tsc` ~8.5 s, ESLint ~5 s, render test ~4 s per component, the site passes build/routes/smoke, second run 3
  hits, 0 engine calls). The rest of the Docker sandbox suite was not rerun (Docker Desktop hung on memory; see
  below).
- **One real run on Antigravity** (`shop-dynamic` + `shop`, `gen_01M63AKY87M697K7P9A7VGK2ET`): the three
  components were generated in parallel (6–7 min each, ~1 M input tokens, mostly re-sent context), each failed one
  isolated check (conventions, `tsc`, ESLint) and passed after one short repair; 6 engine calls, ~$1.82 estimated,
  0 fallbacks, all cached. `generate_frontend` 9 min (the engine-written frontend took ~19.5 min plus a ~4 min
  repair), site checks passed first time, **frontend lane 10 min**. The backend lane was cancelled by the 900 s
  integration wait that starts when the frontend completes (4 modules × ~10 min on Antigravity); moved to 17.6.
- **Not done:** the cache-hit run on the full stack (covered by the tests above); a tighter prompt (the engine
  read ~33 files per component) is a cost follow-up.
