# Story 19.9 — Journey tests on mocks and on the live API

**Epic:** [19 — Real photos and API-driven dynamic apps](epic19_photos_and_live_apps.md) · **Requirements:** FR-32, FR-11 · **Depends on:** 19.8, 14.2

## User story

As a user, I want the generation to prove that my journeys work in the browser, first on the mock API and then
against the real backend, so that "completed" means the app does what I asked, not only that its pages load.

## Context

- Frontend checks: `orchestrator/frontend_validation.py` (`frontend:tests` runs vitest and the Playwright smoke
  test generated by `frontend_codegen.smoke_spec`); failures go to `repair_frontend`.
- Live checks: `orchestrator/integration.py` runs `run_playwright_live_smoke` against the live frontend through
  `_proxy_command`; a failed live check sets the integration lane FAILED (no repair).
- Hooks from 19.6: `data-bga-section`, `data-bga-record`, `data-bga-action`.

## Steps

1. **Generated spec.** `frontend_codegen.journeys_spec(plan, spec, contract) -> str | None` writes
   `tests/e2e/journeys.spec.ts`: one Playwright test per journey, steps in order:
   - `visit` → `page.goto(route)` (route params from the first fixture record, as the smoke test does);
   - `open` → click the record's link inside `[data-bga-section=…] [data-bga-record]`;
   - `submit` → fill fields by name, submit, wait for the success state (toast or navigation from `onSuccess`);
   - `action` → click `[data-bga-action=…]` (on the chosen record), accept the confirm dialog if any;
   - `expect` → text visible / record count / a field's shown value changed compared with its value read before
     the previous mutating step. `$unique` becomes a per-run value, so tests create their own records and do not
     depend on seed order.
   Each step is wrapped in `test.step("<journey>: <n> <do>")`, so failures name the step. Generator-owned file.
2. **On mocks** (`validate_frontend`): new check `frontend:journeys` after `frontend:tests`, running only the
   journeys spec; `live: true` expectations are skipped (`test.skip` inside the step with a note). Failures go to
   `repair_frontend` with the failing journey, step, selector and the page's screenshot path, like other checks.
3. **On the live API** (`integrate`): after the live smoke, `integration:journeys` runs the same spec against the
   live frontend preview (reuse `_proxy_command`), with `live: true` expectations enabled. A failure sets the
   integration lane FAILED with the journey and step in the reason; the report and the UI show it. A live repair
   loop is out of scope (note it as a follow-up in the Status).
4. **Time limits.** Settings `journey_test_timeout_seconds: int = 180` (whole run) and a per-step timeout of 15 s
   in the spec. Record the measured times.
5. **Results.** `validation_runs` / check details carry per-journey, per-step results; the generation result page
   in `agent-ui` lists journeys with pass / fail / skipped per step (mocks and live side by side).
6. Tests: snapshot of the generated spec for the flashcards golden pair; Python unit tests for each step kind's
   code; sandbox test running `frontend:journeys` on the golden site (mocks); a fake dynamic run of the flashcards
   pair where `integration:journeys` passes live (rating a card moves `dueDate`) and, with a deliberately broken
   fake `card.review`, fails at the right step.

## Acceptance criteria

- [ ] Every journey becomes a Playwright test whose steps are named in failures.
- [ ] `frontend:journeys` runs on mocks (live-only expectations skipped) and failures reach `repair_frontend`.
- [ ] `integration:journeys` runs on the live API; failures fail the integration lane with the step named.
- [ ] Results per journey and step are stored and shown in the UI.
- [ ] Sandbox and fake-run tests above pass, including the deliberate failure.

## Verify

`make lint`, `make test`, `BGA_SANDBOX_TESTS=1 make test`, `cd agent-ui && pnpm exec tsc --noEmit && pnpm lint`,
`make up` with the fake engine: the flashcards pair COMPLETED with journeys passing on mocks and live.
